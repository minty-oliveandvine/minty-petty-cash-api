# Petty Cash API - what minty-petty-cash-web calls

This service is the Django home of the bearer JSON API minty-petty-cash-web (port 3010) reads and writes a company's petty cash through. Until it took over, the API lived in Flask as the blueprint `blueprints/petty_cash_api/` (Minty branch `petty-cash-api`; its own `docs/features/petty-cash-api.md`). **The paths and the JSON are Flask's, byte for byte**: the web app moves by changing `PETTY_CASH_API_URL` alone (owner, 2026-10-14). Flask stays the only token minter (`/handoff/petty-cash-web`) and the only holder of Xero credentials.

Status (2026-10-15): the door and every step of the report wizard are ported - Opening to Submit and the outcome - each proved by tests and by `scripts/parity.py` against Flask (MATCH on three local companies). On 2026-10-15 minty-petty-cash-web's `development` was walked through a whole day against this service (E2E Petty Cash Shop, 2026-10-14: Opening, Sales, an expense with a receipt, Deposit, a short count with its reason, Ending, Finish) - every call answered here, every page checked at 360, 768 and 1440 px. Every route Flask's Petty Cash API serves is now served here.

## The one public read: `GET /api/petty-cash/v1/public/share/{initials}/{date}/{secret}`

Flask's same route (its `docs/features/petty-cash-api.md`), ported 1:1 as a database-only read (`routes/public_share.py`, mounted at `/public` in `petty_cash/api.py`): the read-only Daily Report a share link shows, for the petty-cash web apps' own public `/share/{path}` page, replacing Flask's `/Minty_Report/{path}/` page.
- **Decided by** `services/share.py::resolve_share`, Flask's check for check: the full path with its 32-character secret, an unexpired row, a token passing `verify_share_token` (Flask's `utils.verify_share_token`, byte for byte, with the shared `SECRET_KEY`) and naming the row's company and day, the company (not archived - an archived company's link is the same 404, and its row is kept for a restore), a submitted report.
- **Answer:** `company_name`, `transaction_date`, `currency_code`, `status`/`status_label`/`status_tone`, `publishing_status`, `submitted_at`, `submitted_by`, `kpis`, `sales {methods [{name, value_name, type, amount}], cash, total}`, `expenses {lines [{item, supplier_name, amount, receipts [{name}]}], total}`, `cash`, `closing_balance`, `expires_at` - the figures are `routes/report.py::report_figures`, the Daily Report's. No ids, permissions, options, line description or receipt access.
- **Refusals:** 404 "This link doesn't work. Ask the person who shared it for a new link." for every reason but an expired link, 410 "This link has expired. Ask the person who shared it for a new link." (the row is deleted; so is one whose token fails its signature). A missing `SECRET_KEY` or any failure is the generic 500.
- **Headers:** `Cache-Control: no-store`, `Referrer-Policy: no-referrer`; CORS through django-cors-headers (the API's origins, no credentials).
- **Logging:** the row id only. The request log blanks the path (`core/middleware.py::loggable_path`), Django's own "Not Found: <path>" warning is skipped for this route (`_has_been_logged`), and a failure logs its type and frames, never its message (a database error's parameters would hold the secret). No rate limit, as in Flask.

`POST /reports/{id}/share-link` answers `{url, path, expires_at}`, as Flask's: the apps build `<their origin>/share/{path}`; `url` is that page on `PETTY_CASH_WEB_URL` (since 2026-10-20 - it was Flask's `/Minty_Report/` page, now only a redirect).

## The door (`core/auth.py`) - fails closed

Every route is under `/api/petty-cash/v1/companies/{entity_id}`. The company comes from that address and nowhere else: not the body, not the token's `entity_id` claim, not a header. `NinjaAPI(auth=PettyCashBearerAuth())` gates every endpoint, so a new route is gated without being told - except the one public read below, the only operation that says `auth=None` (`tests/test_public_share.py` pins that). Checks, in Flask's `guard.py` order:

| Check | Refusal |
|---|---|
| A preflight | answered by django-cors-headers (`200` - Flask answered `204`), no token needed |
| A valid HS256 token (the shared `SECRET_KEY`, 60 s clock leeway) carrying `module == "billing"` (Flask's `MODULE_TOKEN_CLAIM`) and a `user_id` | `401 {"error": "unauthorized"}` |
| The person exists and is `approved` | `401` |
| Membership (an approved `user_entity` row), or a system superuser. A stranger, an unknown id and a malformed id all get the same answer. | `403` "You don't have access to that company." |
| The company is not archived (`entities.archived_at`, owner 2026-11-10; `company_for`). Refused for superusers too, with the same answer as a stranger, so nothing says it exists | `403` "You don't have access to that company." |
| The company is past onboarding | `409` "This company is still setting up. Finish setting it up to use Petty Cash." |
| Petty Cash is on (`core/entitlements.py`, every unknown answers no) | `403` "Petty Cash isn't switched on for this company. An admin can turn it on in the company's modules." |

**Responses** (`core/exceptions.py`, `core/middleware.py`): always JSON. A refusal is `{"error": "<sentence>"}` - a sentence the app shows as it stands - sometimes with `to`, `field` or `report_id` the app routes on. `unauthorized` sends the app back through Flask's hand-off. A 500 says "Something went wrong on our side. Please try again." and the detail goes to the log only. An unknown path is a JSON `404`. Every response is `Cache-Control: no-store`.

**CORS**: `PETTY_CASH_WEB_URL` (default `http://localhost:3010`) and `MINTY_WEB_URL` (default `http://localhost:3000`; the hub holds Petty Cash Settings since 2026-11-10, owner; `CORS_ALLOWED_ORIGINS` replaces both) and a `pettycash` preview set where `PREVIEW_ORIGIN_REGEX` allows it (`config/preview_origin.py`, refuses to boot on a pattern that could match other hosts); methods `GET, POST, PUT, PATCH, DELETE, OPTIONS`; headers `authorization, content-type` (no `x-entity-id`). Refusals carry CORS too, so the app can see its 401.

## Stale drafts (owner, 2026-10-26)

A **stale draft** is a draft dated before the company's last submitted report
(`services/reports.py`: `live_drafts`, `is_stale_draft`). Days go in order, so it can never be
finished, and it used to block the company for good: any draft hid Start New Report and sent
Continue to its old date (Dine at Venus, 2026-10-20).
- **`GET /home`:** `draft` and `draft_date` come from live drafts only. Opening's no-date
  fallback (the latest draft of the last 7 days) ignores stale drafts too.
- **`POST /reports/submit`** refuses one with 409, `to: "dashboard"`: "This draft is for {day},
  before your last submitted report ({last}). Days go in order, so it can't be submitted - delete
  it from Report History." The close read shows the same `problem`.
- **`DELETE /reports/{id}`** accepts one even though it is not the latest report (same
  permissions: own = cashier and up, anyone's = shop manager and up). It leaves the previous
  report's `next_transaction_date` alone, since the sequence has moved past it. The Daily Report
  and the history row say `delete: true` for it. A non-latest *submitted* report is still
  refused.
- **Deliberately different from Flask**, whose `entity/services/dashboard.py` still counts every
  draft. Only the unused `petty_cash_api` blueprint reads it, so `scripts/parity.py` would show a
  `/home` DIFF for a company that has a stale draft.
- Tests: `test_home.py`, `test_opening.py`, `test_close.py`, `test_report.py`, `test_history.py`
  (the "stale" cases).

## What this service writes

The day's report and what hangs off it - `report`, `share_link`, and on delete `xero_report_sync`, `xero_bank_transfer`, `xero_bank_transaction`, `report_sale`, `report_expense`, `attachment`, `report_expense_attachment`, `report_cash_count`, `report_history` - plus `entity_cash_detail` on submit, a `xero_contact_sync` row for a new supplier, and from Settings `entity_sale_setting` and new `sale_info` catalogue rows. Everything else is read-only. The models are minty-db's (`minty_db.models`, pinned `v0.3` in `requirements.txt`; ids are `uuid.UUID` since 2026-10-30), and this service's own behaviour over them (role labels, the cash sales method's name) lives in `core/roles.py` and `services/sales.py`. Deliberately not copied from Flask: the denomination resolver's write of a company's order onto the shared `cash_info` rows, and `log_history`'s separate commit that swallowed errors.

## Parity with Flask (`scripts/parity.py`)

`python scripts/parity.py --entity <id> --user <id> --day YYYY-MM-DD [--report <id> ...] [--share-link <share_link row id>]` sends the same reads, with the same minted token, to Flask (`--flask`, default `http://127.0.0.1:5010`) and to this service (`--django`, default `http://127.0.0.1:8010`) on one database, and compares the JSON field by field (a CSV answer - `GET /reports/export.csv`, asked with no dates and with the 366 days ending on `--day` - byte for byte, plus `Content-Type` and `Content-Disposition`): `MATCH`, `DIFF` (with the fields) or `NOT PORTED`. `EXPECTED_DIFFS` names the differences that are meant (today: `/home`'s `draft.last_edit_seconds`, timing, and its `start_date`, which Flask does not send). A route counts as ported only once parity says MATCH. `--share-link` compares the public read of an EXISTING `share_link` row (its path read from the database, never printed) and an unknown secret beside it - sent only when the row is unexpired and its token passes, since reading it otherwise deletes it; never create a link for the run. Writes are compared by the tests, not by parity: both services share the database, so a write through one changes what the other reads.

## Publish reasons (`services/publish_reasons.py`, 2026-11-05)

Why a failed report didn't publish, and whether each reason is fixed now. Ported from Flask in Phase 3
of the Flask retirement (`history_query.publish_reasons_for`, `publish_errors`, `publish_resolution`);
until then they were asked of Flask's `POST /api/internal/xero/publish-reasons`.

- **The stored reasons:** the newest `report_history` row with `action = "publish_failed"`. Its
  `new_value` is a JSON list of items `{text, scope, expense_id, deps, ...}`. Older rows hold plain
  strings, or the reason in the action (`publish_failed: ...`).
- **An expense line's reason** is fixed when every line it names has an ACTIVE contact and an
  account that is not known to be inactive. A removed line counts as fixed; an unknown code is not
  held against the person. A text-only row finds its line by the name in `Expense '<item>'`.
- **A company-wide reason** re-checks its `deps`: an account role mapped to an ACTIVE `account_info`
  row, or a contact role mapped to an active contact. A legacy reason infers its deps from its
  wording (cash sale, discrepancy, deposit, withdrawal/director). Anything else stays unresolved.
- **Contacts are asked of live Xero** (`GET /Contacts/{id}` with the token from accounts-api's token
  service), once per contact per answer. When Xero or the token service can't answer, the synced
  `xero_contact_sync` table answers instead.
- **Accounts are the database's word:** archived accounts leave `account_info` on sync.
- A re-check that fails is logged and the reason reads unresolved; the page never fails over a
  badge. So the history no longer has the 503 it had when Flask could not be asked.
